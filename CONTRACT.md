# Tasks shared service contract

The desktop UI, CLI and MCP use `tasks_core::TaskService` exclusively. API:
`TaskService::open(path: impl AsRef<Path>) -> Result<Self, ServiceError>`;
`service.execute(action: &str, input: serde_json::Value) -> Result<Value, ServiceError>`.
`tasks_core::default_db_path() -> PathBuf` honors TASKS_DB, otherwise ~/Library/Application Support/com.dwenn.tasks/tasks.sqlite3 on macOS (platform equivalent elsewhere).
Service is cheaply cloneable (path owned), Send + Sync; each call opens a configured connection. Blocking database operations must not run on Tauri's UI thread.

JSON uses snake_case. IDs are UUID strings except built-in list `inbox`.

Task: {id,title,notes,list_id,parent_id,due_date,due_time,reminder_at,priority,position,completed_at,deleted_at,created_at,updated_at,version}.
Dates: YYYY-MM-DD; due_time: HH:MM or null; reminder_at: RFC3339 UTC or null. Timestamps RFC3339 UTC. priority: 0 none, 1 low, 2 medium, 3 high. position integer. Notes plain text/Markdown. Nullable fields are always present in responses. Version increments on mutation.
Folder: {id,name,parent_id,position,created_at,updated_at}.
TaskList: {id,name,folder_id,color,position,created_at,updated_at}. Inbox protected.

Actions:
- snapshot {} -> {tasks: Task[],lists: TaskList[],folders: Folder[],settings: object,revision: integer}. Includes completed and soft deleted tasks for small local datasets.
- revision {} -> {revision: integer}
- tasks.list {view?: inbox|today|upcoming|all|completed|trash, list_id?, search?, date?: YYYY-MM-DD} -> Task[]. Default all active tasks; date must be caller-local today. Search title+notes. Today includes overdue. Upcoming next 7 days including today. Inbox/all show top-level tasks by default. Today/upcoming include due subtasks. Completed/trash show children independently in that state, while suppressing descendants whose parent shares the state. Explicit include_subtasks false forces roots; true returns all. Optional parent_id filters direct children.
- tasks.get {id} -> Task
- tasks.create {title,list_id?: inbox,parent_id?,notes?,due_date?,due_time?,reminder_at?,priority?} -> Task. Child inherits parent's list.
- tasks.update {id,title?,notes?,list_id?,parent_id?,due_date?,due_time?,reminder_at?,priority?,expected_version?} -> Task. Omitted unchanged; null clears nullable fields. Moves/completion/deletion propagate to descendants transactionally. Cycles rejected.
- tasks.complete {id,completed?: true} -> Task. true completes descendants, false reopens task and required ancestors.
- tasks.delete {id} -> Task. Recoverable soft delete subtree.
- tasks.restore {id} -> Task. Restore subtree and required ancestors.
- tasks.reorder {ids: string[]} -> {ok:true}; reorder listed sibling tasks atomically; reject mixed parent/list groups, duplicates or missing IDs.
- folders.create {name,parent_id?} -> Folder
- folders.update {id,name?,parent_id?} -> Folder; reject cycles.
- folders.delete {id} -> {ok:true}; move child folders/lists to deleted folder's parent (preserve tasks).
- folders.reorder {ids:string[]} -> {ok:true}; sibling scope.
- lists.create {name,folder_id?,color?} -> TaskList
- lists.update {id,name?,folder_id?,color?} -> TaskList
- lists.delete {id} -> {ok:true}; moves tasks to inbox, removes list; reject inbox deletion.
- lists.reorder {ids:string[]} -> {ok:true}; sibling scope.
- settings.set {key,value} -> {ok:true}. Allowed: theme (system|light|dark), notifications (boolean), sidebar_width (number), list_width (number). Defaults theme light, notifications false.
- reminders.due {now?: RFC3339} -> Task[]; only active reminders due, not already notified.
- reminders.mark {id,reminder_at,generation} -> {ok:true}; mark only matching reminder after successful send.

All mutations are transactional. Domain mutations increment the persisted application revision; sync exports, local checkpoint writes and merges without visible changes do not. SQL migrations are numbered via user_version with foreign keys, WAL and busy_timeout. Invalid input returns human-readable errors, not panic. Empty initial DB contains only Inbox, no mock/demo tasks. CLI and MCP may seed a separate QA database. The core, CLI and MCP do not perform network access. The desktop can optionally exchange personal sync packets directly with an explicitly connected Google Drive or Dropbox account.

Tauri single command: `dispatch({action, input})` returns service JSON result or error string. Frontend adapter uses `invoke('dispatch', {action,input})` in Tauri. Web preview mode explicitly separate in-memory/demo test adapter; production always SQLite. Root owns Tauri config, package.json, Vite and integration. Frontend agent owns src/ (except adapter.ts and types.ts owned by root). Backend agent owns crates/tasks-core. CLI agent owns crates/tasks-cli and crates/tasks-mcp, protocol integration tests, docs for CLI/MCP. Workspace Cargo.toml owned by root.

## Tasks feature extension (schema v2)

Existing records are migrated in place. All additions are optional in create/update requests, always emitted in responses. Task gains:
- `start_date: string|null` (YYYY-MM-DD), `start_time:string|null` (HH:MM), `duration_minutes:number|null` (1..525600), `timezone:string` IANA (defaults to system zone).
- `recurrence: {frequency:'daily'|'weekly'|'monthly'|'yearly',interval:number,weekdays:number[],end_date:string|null,count:number|null,mode:'due_date'|'completion_date'}|null`. ISO weekdays 1 Monday..7 Sunday; weekly only. Due date required. Completion creates exactly one next occurrence atomically, with reset subtasks and preserved tag/attachment/checklist content. `recurrence_next_id:string|null` identifies that next occurrence; repeated completion is idempotent. Short months clamp to their last day; local times preserve timezone across DST.
- `reminders:string[]` of absolute RFC3339 timestamps, canonical UTC, maximum 20. `reminder_at` remains backward-compatible first reminder. Supplying reminders replaces the reminder set; supplying reminder_at alone replaces with zero/one. `reminders.due` returns task-shaped entries with `reminder_at` set to each due unacknowledged occurrence; `reminders.mark` acknowledges exactly that timestamp. Native worker needs no shape change.
- `tag_ids:string[]`, `linked_task_ids:string[]`, `attachments:Attachment[]`.
- `notes_format:'plain'|'markdown'|'html'` (default plain), `checklist:{id:string,text:string,completed:boolean}[]` (ordered; maximum 1000), `pinned:boolean`, `wont_do_at:string|null`, `section_id:string|null`.
- Tasks.create/update accept these editable fields: start_date,start_time,duration_minutes,timezone,recurrence,reminders,tag_ids,notes_format,checklist,pinned,section_id. readonly fields wont_do_at/recurrence_next_id are changed by explicit actions. Existing expected_version semantics cover all edits.

`TaskList` gains `archived_at:string|null`, `view_mode:'list'|'board'|'timeline'`, `group_by:'none'|'section'|'date'|'priority'|'list'|'tag'`, `sort_by:'manual'|'due_date'|'priority'|'title'|'created_at'`, `sort_order:'asc'|'desc'`. List create/update accept preferences. Archive via `lists.archive {id,archived?:true}`; protected Inbox remains unchanged. Snapshot includes archived lists; ordinary task queries omit their tasks unless list_id explicitly provided or view completed/trash.

Snapshot gains `tags:Tag[]`, `sections:Section[]`, `templates:Template[]`. Tags `{id,name,color,position,created_at,updated_at}`. Sections `{id,list_id,name,position,created_at,updated_at}`. Attachments `{id,task_id,name,mime_type,size,created_at}` (never binary content in snapshot). Templates `{id,name,task:object,created_at,updated_at}`.

New actions:
- `tasks.duplicate {id,list_id?,title?}` -> cloned Task with cloned subtasks/checklist/tags/attachments, cleared completion/trash/wont-do/recurrence-next state.
- `tasks.wont_do {id,wont_do?:true}` -> Task; dismiss subtree, or reactivate task + required ancestors. `tasks.list view:'wont_do'` exposes this view with subtree deduplication.
- `tasks.tags {id,tag_ids:string[],expected_version?:number}` -> Task.
- `tags.list {}`, `tags.create {name,color?}`, `tags.update {id,name?,color?}`, `tags.delete {id}`; tag names unique case-insensitively; deletion only removes associations.
- `links.add {id,linked_task_id}`, `links.remove {id,linked_task_id}` -> `{ok:true}`. Bidirectional independent task links; no self links.
- `attachments.add {id:task_id,name,mime_type?,content_base64}` or `attachments.import {task_id,path}` -> Attachment. Maximum 20 MiB per file. Bytes are stored in SQLite transactionally; no external cloud. `attachments.get {id:attachment_id}` -> Attachment + content_base64; `attachments.remove {id:attachment_id}` -> `{ok:true}`. Opening/downloading bytes is a desktop adapter action, not an arbitrary filesystem-write service operation.
- `sections.create {list_id,name}`, `sections.update {id,name?}`, `sections.delete {id}`, `sections.reorder {ids}`. Deleting a section clears task section assignments. Moving a task across lists clears incompatible section assignment and descendants' assignments.
- `templates.create {name,task_id}` -> Template; `templates.update {id,name?}`, `templates.delete {id}`, `templates.apply {id,list_id?}` -> Task. Template captures one task + subtree as editable creation data; apply creates new UUIDs.

Settings additions (settings.set key/value; snapshot.settings includes defaults):
- smart_lists object values show|hide|auto; keys all,today,tomorrow,upcoming,inbox,completed,trash,wont_do,assigned,summary,tags,filters. Default today/upcoming/inbox/completed/trash/tags/filters show; all/tomorrow hide; other entries auto.
- theme_color default|sky|turquoise|teal|matcha|sunshine|peach|lilac|ebony|navy|gray|dark (default default).
- font_size normal|large|extra-large (normal); sidebar_count all|tasks|hidden (all); completed_style default|strikethrough (strikethrough); show_list_color bool (true); completion_sound bool (true).
- week_start 0|1|6 (1); show_week_numbers bool (false); time_format 12|24 (24).
- date_recognition off|keep|remove (remove); tag_recognition keep|remove (remove).
- default_priority integer0..3 (0); default_list_id existing list ID (inbox); default_tag_id existing tag ID|null (null); default_date none|today|tomorrow (none).
- default_reminder_timed none|on-time|5m|15m|30m|1h (none); default_reminder_allday none|09:00|18:00 (none); default_add_to top|bottom (top); overdue_position top|bottom (top).
- `view_preferences` object keyed today,upcoming,all,inbox,completed,trash,wont_do,tag:<uuid>,filter:<uuid>; each value same group_by/sort_by/sort_order/view_mode enum fields as TaskList. All unknown settings remain rejected.

### Final extension clarifications

- Latest SQLite schema is **9**: v2 adds task features, v3 adds comment/attachment associations, v4 materializes template previews so binary payloads are never read for normal snapshots, v5 adds reminder generation tokens and comment versions, v6 adds list/folder metadata and note-list types, v7 adds task activities, v8 adds pending reminder actions, and v9 adds opt-in personal sync metadata, causal registers and materialization baselines. All earlier versions migrate forward transactionally.
- `recurrence.anchor_date:string|null` is preserved to prevent January-31 or February-29 series from drifting after shorter months. The service sets it from the first due date when absent. Interval 1..365; count 1..1000000 or null.
- Duplicate creates fresh task/checklist IDs, resets checklist checked states, completion/trash/won't-do status, and copies tags/attachment bytes. Comments and independent links are not copied. Duplicating a trashed subtree restores the copy's descendants too.
- `attachments.read_chunk {id,offset?:0,length?:262144}` returns attachment metadata plus content_base64, offset, next_offset:number|null; raw-byte offsets, at most256KiB decoded per response.
- Task gains `comments:{id,task_id,body,attachment_ids:string[],author:'You',created_at,updated_at}[]`. `comments.list {id:task_id}`, `comments.add {id:task_id,body?:'',attachment_ids?:[]}`, `comments.update {id:comment_id,body?,attachment_ids?}`, `comments.delete {id:comment_id}`. Comments require text or at least one attachment, maximum10000 text characters/20 files. Attachment IDs must belong to same task. Omitted fields remain unchanged; deleting an attachment clears its comment association.
- `templates.list {}` and `templates.get {id}` return previews with nested subtasks, without binary file content. Applying a template preserves captured attachment bytes independently from its source task.
- `tasks.list` also accepts view tomorrow|wont_do, tag_id and section_id. Omitted section_id filters nothing; explicit null filters unsectioned tasks.
- Settings include `show_timezone:boolean` defaultfalse, and `hotkeys:object` default{} with action IDs quick_add,search,settings,shortcuts,complete_task,delete_task,add_subtask,today,tomorrow,upcoming,inbox,all,completed,wont_do,trash. Empty string disables; normalized chords such as mod+n or sequences g t.
- Settings include `saved_filters: {id,name,list_ids:string[],tag_ids:string[],priorities:number[],date:'all'|'today'|'tomorrow'|'week'|'overdue'|'undated',match:'all'|'any'}[]`, default[], maximum100. References are checked on save and pruned on list/tag deletion.
- First assignment of a due date/time to a previously undated task applies the saved default reminder if no reminders existed and reminders/reminder_at is omitted. Explicit reminders:[] opts out. Later edits preserve user choices.

- `reminders.due` adds `reminder_generation:string` to each returned due entry. `reminders.mark {id,reminder_at,generation}` requires this exact token; removing/rearming a reminder creates a new generation even at the same timestamp. A stale ACK is an idempotent no-op.
- Comment responses include `version:number`. `comments.update/delete` accept optional `expected_version` and reject stale writes; GUI editors capture it at edit start. `tasks.tags` accepts the task's expected_version too.
- Ordinary duplication of an active subtree excludes independently trashed descendants. Duplicating a trashed root copies its subtree as active work. Rich HTML and Markdown note checkboxes reset in duplicates, new recurring occurrences and applied templates.
- When a recurring parent advances, historical child occurrences with successors are omitted; independently recurring children advance only their latest occurrence according to their own schedule/count. Exhausted child series are not restarted.

### Custom monthly and yearly calendar patterns

Recurrence JSON adds optional fields without a schema migration. Newly normalized rules emit `month_days:[]`, `ordinal_weekday:null`, `workday:null`, `year_month:null`, `skip_weekends:false` when unset; old persisted rules may omit them.

- `month_days:number[]`: monthly selected dates1..31 and -1 for Last Day; sorted/deduplicated, maximum32 entries. Yearly accepts one date1..31. Explicit dates absent in a month skip that month; rules without any custom pattern retain their existing clamp-to-month-end behavior.
- `ordinal_weekday:{ordinal:number,weekday:number}|null`: ordinal1..5 or -1 for Last; ISO weekday1 Monday..7 Sunday. Monthly or yearly. A missing fifth weekday skips the period.
- `workday:'first'|'last'|null`: monthly first or last Monday–Friday; does not infer regional holidays.
- `year_month:number|null`: selected annual month1..12, used with month_days or ordinal_weekday. Impossible month/day combinations are rejected; February29 skips nonleap years.
- `skip_weekends:boolean`: monthly calendar-date patterns omit weekend occurrences entirely. It does not move them to Friday/Monday and cannot combine with ordinal_weekday/workday.
- month_days, ordinal_weekday and workday are mutually exclusive. Multiple monthly dates progress within the current eligible month before advancing by interval months. Annual rules advance by interval years. Completion-date mode reanchors eligible periods to the completion calendar; due-date mode advances exactly one matching occurrence from the due date. Only generated occurrences consume count; end_date remains inclusive. Creation of successors remains transactional and idempotent across writers.
- New due-date calendar configurations reject patterns with no possible occurrence in their reachable Gregorian400-year cycle (for example annual31April, or February29 every4years anchored to2025). Validation is independent of exhausted count/end limits. Existing saved impossible schedules remain editable and can complete; they end without a successor. Completion-based patterns are evaluated against their actual completion calendar and also end cleanly if no successor exists.

`recurrence.preview {due_date,recurrence,timezone?,range_start,range_end,limit?:128}` is a pure read-only draft calculation, with no database connection, write, migration or revision change. All dates use YYYY-MM-DD; timezone, when supplied, must be IANA. Recurrence may be null. The inclusive visible range is at most366days; limit is1..512. Result: `{dates:string[],truncated:boolean,assumption:'due_date'|'completion_on_due_date'}`. It returns only future occurrences (the initial due date is excluded), reusing the completion successor engine with identical calendar/count/end semantics and preserved original anchor. Completion-date rules project completion on each due date and label that assumption explicitly. Enumeration is capped at10000successor steps; truncated=true signals either this bound or more in-range dates than the requested limit. Empty/nonrecurring/exhausted schedules return dates:[] and truncated:false.

### Native list and note metadata (schema v6)

- TaskList adds `icon:string` (default empty, null input normalizes to empty, maximum64 characters, no control characters), `pinned:boolean` (false), `show_in_smart_lists:boolean` (true), `list_type:'task'|'note'` (task). `lists.create/update` accept each field. List color accepts empty string for None; omitted create color defaults empty. Tags still require a hexadecimal color.
- Folder adds `icon:string` and `pinned:boolean` with the same defaults/validation. `folders.create/update` accept them. Pinned lists/folders sort before unpinned siblings while retaining their manual position. `folders.delete` is the native Ungroup action and preserves child lists/tasks.
- Task adds `is_note:boolean`; create/update accept it. New items in a note list default to notes unless explicitly overridden. Changing a list type preserves existing item kinds. Converting a task to a note preserves dates, reminders, notes and relationships.
- `lists.duplicate {id,name?,folder_id?}` returns the new TaskList. Default name is the source name plus ` (copy)` and destination is the source folder. Copies icon/color/type/preferences/smart visibility, but starts unpinned and unarchived. Clones sections and every nontrashed task/subtask with fresh IDs, preserving task status, notes/checklist checked states, tags, attachment bytes and recurrence history. Internal task links and recurrence edges are remapped to copied IDs; external linked-task references remain external. Comments and trashed tasks are excluded.
- Active smart queries omit tasks in archived lists or lists with show_in_smart_lists:false. Explicit list_id, nonnull parent_id, nonempty global search and completed/trash/wont_do views bypass this omission. Explicit parent_id:null still follows normal smart-root visibility. Tag/filter smart views follow the same active smart-list visibility rule.
- Task adds readonly `notes_text:string`, derived from stored notes and notes_format. HTML entities are decoded and formatting tags omitted; Markdown yields visible text including literal code; plain notes retain their exact text. Search uses this projection and normalizes whitespace for matching. Stored source notes are never rewritten by projection.
- Native settings: `interface_style:'card'|'flat'` (card), `app_icon:'default'|'rounded'` (default), `show_dock_icon:boolean` (true), `dock_count:'none'|'today'|'inbox'|'all'|'overdue'` (today). Snapshot supplies missing defaults for existing databases without a schema migration or revision change; explicit saved settings take precedence. Dock badges count active tasks, excluding is_note items.
- Native integration preferences: `launch_at_login:boolean` (false), `launch_minimized:boolean` (false), `global_quick_add_shortcut:string` (empty/disabled). All clients share validation and SQLite persistence; only the running desktop performs OS registration. The GUI native setter registers first and persists only on success, restoring previous native state if SQLite fails. A conflict keeps the previous shortcut. Startup registration errors are visible without preventing Tasks from opening.
- `settings.get {}` returns the same merged settings object as snapshot.settings without loading tasks, attachments or navigation. It is read-only and does not increment revision; native startup/preferences and MCP get_settings use this lightweight action.
- Global shortcuts use one canonical lowercase chord: optional modifiers in order `mod`, `ctrl`, `alt`, `shift`, then one key. Require at least mod/ctrl/alt. Allowed keys: a–z, 0–9, f1–f24, space, enter, tab, backspace, delete, escape, arrowup/down/left/right, home, end, pageup/down. Empty clears; sequences, duplicate modifiers and reserved macOS quit/hide/window/system combinations are rejected. `validate_desktop_integration_setting` is exported for native validation before OS effects.
- Native autostart uses Tauri's LaunchAgent manager with `--tasks-autostart`. Only an automatic launch with `launch_minimized:true` starts the main window hidden; normal launches are unchanged. Login startup can be managed only by a packaged release app using the default database. Development or TASKS_DB-isolated sessions never read, enable, disable or roll back the production login item. The shortcut is registered only when nonempty, triggers Quick Add on key press, and is removed on clear or process exit.
- Local `hotkeys` also accepts print_task,set_date,pin_task,clear_date,set_today,set_tomorrow,set_next_week,priority_none,priority_low,priority_medium,priority_high,list_view,kanban_view. Defaults live in frontend `defaultHotkeys`; new observed chords are Print mod+p, Set Date mod+d, List View v l, Kanban View v k. Other newly configurable actions start unassigned. Printable ASCII punctuation is accepted for shortcuts such as mod+, and ?.


## Task feature sprint (schemas v7–v8)

- Task adds `progress:integer` (0–100) and readonly `progress_mode:'manual'|'checklist'`. Effective progress derives from native checklist items and actual HTML/Markdown task items when present, and is 100 for completed tasks. Explicit manual `progress:100` in create/update completes a normal task through the same completion/recurrence service; retrying does not generate another successor. A checklist reaching 100 does not implicitly complete the task. Manual progress survives unrelated updates; duplicates, templates and recurring successors start at zero. Reopening clears manual progress.
- `tasks.activities {id,before_id?:positive integer,limit?:1..100}` returns `{items,next_before_id,task_version,task_deleted}`. Items contain `{id,action,created_at,changed_fields,before,after}`. Title, notes and notes format form one `content` delta. The history starts at migration v7; no history is fabricated for earlier edits. Relationship and lifecycle changes participate in the same transaction; attachment binary content is excluded.
- `tasks.restore_content {id,activity_id,side:'before'|'after',expected_version}` returns the updated Task. It restores title/notes/format only, rejects stale task versions and activity records belonging to a different task, and records the restore action.
- `reminders.capture {now?:RFC3339}` atomically captures due reminders for the persistent action queue and marks their original deliveries. `reminders.pending {}` returns current pending controls. `reminders.resolve {id,reminder_at,generation,action:'done'|'dismiss'|'snooze',minutes?}` resolves one current reminder. Snooze minutes must be 1–10080; Done uses normal completion/recurrence semantics; Dismiss leaves the task active. Generation checks and lifecycle invalidation reject old controls after rescheduling, completion/reopening, trash/restoration or list archival.
- `settings.summary_templates` stores at most 100 named Summary presets. Presets contain an ID, name and validated options for date range/basis, list/tag/status/priority filters, grouping/sorting, subtasks and selected output fields. Relative ranges are recalculated when a preset is applied.
- Timeline is a list presentation preference, persisted through list create/update. Smart filter presentations can also select Timeline through `view_preferences`. Timeline date mutations use normal task updates with an expected version; moving an interval preserves local times and recalculates elapsed duration across DST.
- Multiline task creation is an explicit frontend review workflow: each chosen line uses the same core create action. A partial failure retains successful IDs and retries only unfinished lines. No all-or-nothing batch action is implied.

## Personal device sync (schema v9, packet protocol v1)

Sync is opt-in. Migration creates only small metadata tables. `sync.status` and checkpoint reads do not copy task or attachment data. The first export or nonempty valid merge activates tracking and captures the existing local data. Subsequent domain writes update changed registers transactionally; immutable attachment content is read/encoded only for newly added attachment IDs during ordinary autosave. Large baseline values use local fingerprints instead of a third content copy.

- `sync.status {}` returns `{enabled:boolean,device_id:string,clock:integer,revision:integer,entities:integer,pending_conflicts:integer,last_merge_at:string|null}`. This is a lightweight metadata read. Its `revision` is specific to local sync state, independent of the application revision; use it for upload debouncing. `clock` alone is not a change token.
- `sync.export {}` returns a deterministic JSON packet: `{protocol:'tasks-sync',version:1,device_id:string,clock:integer,vector:{[device_id]:integer},entities:Entity[]}`. An entity is `{kind:string,id:string,fields:{[column]:Version[]}}`; a version is `{device_id:string,clock:integer,context:{[device_id]:integer},value:JSON}`. Each register contains its active causal alternatives. `$exists` is the live/deleted register. Composite relation IDs are canonical JSON arrays of their key fields. Unchanged state produces identical packet content. Exports contain full known replica state, including tombstones; they are not SQLite file copies.
- `sync.merge {packets:Packet[],checkpoint_provider?:'google_drive'|'dropbox',expected_checkpoint?:string}` validates and merges the entire batch in one transaction. The two checkpoint fields must be supplied together. Result: `{merged:integer,changed:boolean,visible_changes:boolean,status:SyncStatus}`. `changed` includes causal state changes; `visible_changes` identifies a change to the materialized domain data. Duplicate/reordered packets do not increment task/comment versions or recreate deleted records. Invalid/unknown protocol versions, fields, types, references or oversized input reject the whole batch without partial changes.
- `sync.conflicts {}` returns `{items:[{kind,id,field,label,winner_id,versions:[{id,device_id,clock,value,truncated}]}]}`. Version IDs are `device_id:clock`. Large values are previewed rather than fully returned; selection still refers to the complete stored value. Binary attachment alternatives are described without returning their base64 bytes. Timestamp-only differences are not presented as content conflicts.
- `sync.resolve {kind,id,field,version_id}` selects one existing conflicting version and writes a new causally dominant version. Result: `{ok:true,status:SyncStatus}`. It rejects missing/stale conflicts. For `$exists`, false means delete and true means keep. The alternatives remain available until resolution or a later explicit edit of that field observes and supersedes them.
- `sync.checkpoint {provider:'google_drive'|'dropbox'}` returns `{token:string|null}`. `sync.checkpoint.set {provider,token}` accepts a 43-character URL-safe token and returns `{ok:true}`. Checkpoints are local, independently scoped per provider, excluded from packets, and do not increment either application or sync revisions. Native transport stores the same token in its local credential/cache record after a successful exchange. A mismatch invalidates its download cache and is passed to merge. Restored/cloned databases with reused device clocks receive a fresh device identity; post-checkpoint local versions are rebased so they remain alternatives instead of being overwritten. The exported device ID after merge is authoritative for the next upload filename.

Replicated entities are folders, lists, tasks, tags, sections, task/tag links, task/task links, reminders (schedule only), comments, comment/attachment links, attachments (including content), templates (including captured attachment content), and only the `saved_filters` and `summary_templates` settings keys. Empty presets on a fresh installation are neutral defaults; an explicit clear after a preset was authored remains a replicated change. All other settings, OAuth/Keychain credentials, delivery generations/notified state, pending reminder controls and native device configuration remain local. Task activity history is local; remote merges/resolutions append normal local history entries without transferring history tables.

Independent fields merge automatically. Concurrent versions of the same field are preserved with a deterministic visible winner. A concurrent hard deletion wins the visible `$exists` register, while its live alternative remains recoverable through conflict resolution. JSON-valued fields such as task details and each portable setting are one register, so concurrent changes inside them can require choosing an alternative. Canonical JSON/default normalization prevents unrelated edits from resolving such a conflict merely because serialization order changed.

The materialized view maintains application invariants while keeping original causal values: references to known deleted lists/folders fall back to Inbox/root, active children survive a concurrent parent deletion, parent cycles are broken deterministically, active descendants reopen completed/Won’t Do ancestors, and known deleted list/tag references are pruned from saved filters. Unknown references reject the merge. Concurrent duplicate tag names receive stable visible disambiguation; duplicate recurrence-source references retain both tasks without violating SQLite uniqueness. Normal optimistic task/comment versions are local and increment on affected remote changes, including association-only comment attachment changes. Existing local reminder delivery state is retained for unchanged schedules; imported schedules receive new local generations.

The core accepts at most 32 packets per merge, 100 MiB per packet, 200 MiB per batch, 100,000 entities, 128 devices and 128 concurrent versions per register; attachments remain limited to 20 MiB each. It rejects implausible clock jumps greater than 1,000,000 beyond local knowledge. The native provider transport currently imposes a stricter 64 MiB packet limit. These limits fail explicitly. Tombstones and unresolved concurrent values are retained; no automatic history/attachment garbage collection is implied by sync. Packet content is not encrypted or signed by this protocol. Cloud transport and account authorization belong to the native layer, which writes only its own per-device packet file and performs no public sharing or collaboration.

## Application updates (native macOS)

`automatic_update_checks:boolean` is a local setting (defaults to true in the native updater); it is not synchronized. Native commands `update_status`, `update_set_automatic {enabled}`, `check_for_updates`, `download_update` and `install_update` own the update state. They do not accept an endpoint, key, URL or archive from the webview. Release archives come from `DwennK/Tasks` and require the configured updater signature. Downloads and installation require separate user actions. Installation waits for every window's save acknowledgement and native activity guards, then locks cancellation while replacing the bundle and restarting. Custom-database sessions, debug builds and browser previews cannot install updates. See [releases](docs/releases.md) for distribution and validation boundaries.
